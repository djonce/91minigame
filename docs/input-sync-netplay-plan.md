# 不传音视频的 ROM 联机方案

日期：2026-09-18。本文保留确认时的设计基线。用户已确认按此路线开发，现已完成本地帧同步测试版；实际完成项、测试证据与真机待测项见[实现与验收](input-sync-netplay-implementation.md)。以下“当前/尚未”描述的是设计时状态。

## 1. 结论与路线选择

**可行。每台手机运行同一款 ROM，通过网络同步带帧号的玩家输入，在本地生成画面和声音。** 三人分别操作 P1/P2/P3，三台设备都模拟完整的一局游戏，而不是各自只计算自己的角色。

建议优先验证这条路线，以降低多人房间的持续网络流量，避免依赖 iOS 微信中的音画采集、编码及播放链路。代价是每个参与者都要运行模拟器，且必须补齐可控的模拟器执行接口、验证一致性。既有单机真机验收不等于这些条件已经满足。

这更新了此前优先验证媒体传输的建议；[多人架构文档](multiplayer-architecture-plan.md) 保留为媒体路线与房间设计参考。最终选型以本文件第 7 节的验证结果为依据，不同时开发两套完整联机产品。

RetroArch 的联机设计已采用交换输入、重放的方式，要求核心具有确定性、内容和核心一致，状态序列化影响恢复与重放能力。这证明该类方案成立，不证明当前 EmulatorJS 的浏览器构建已具备可用接口。[Libretro 官方设计](https://docs.libretro.com/development/retroarch/netplay/)

## 2. 同步什么

| 数据 | 用途与时机 |
| --- | --- |
| ROM、核心及配置摘要 | 入房检查同一个游戏、运行包和设备配置；ROM/核心仍需事先下载或命中本地缓存 |
| 初始完整模拟器状态 | 所有人从同一状态、同一帧开始；处理 SRAM 等持久化数据差异，不能各读自己的本地存档 |
| 每帧各席位的按键状态 | 持续交换方向、A/B、START/SELECT；包含帧号，不用网络到达时间决定生效时间 |
| 已确认帧的状态摘要 | 检测分歧；仅在所有输入已确定的同一帧比较，不比较尚在预测的当前帧 |
| 恢复快照与后续输入 | 初始加入、重连或发现分歧时使用；不持续传送每帧完整存档 |
| 房间控制事件 | 准备、开始、暂停、退出及席位变更；带会话代数和统一生效帧/屏障 |

例如第 1800 帧的输入是「P1 向右、P2 按 A、P3 无按键」，三台设备都把这组输入应用到该帧。相同初始状态、相同核心和配置、相同输入顺序，经过确定性验证后，才能依赖三端算出相同结果。

只同步关卡、分数或角色位置不够：CPU、内存、计时器、敌人、子弹和随机状态等都会影响后续结果。任意 ROM 没有统一的“敌人死亡/进入下一关”语义接口；逐游戏逆向这些事件不作为统一接入规范。这里的“进度”应指完整模拟器快照与帧进度。

## 3. 延迟同步与回滚

| 方式 | 运作方式 | 适用阶段 |
| --- | --- | --- |
| 等待输入的帧同步 | 预留少量输入延迟；某帧的所有玩家输入齐全后，各端才执行该帧 | 首个可验证原型，逻辑更容易检查；慢网或慢设备会让全局等待 |
| 预测与回滚 | 先预测未到达的远端输入；发现预测错误后恢复历史状态，按正确输入重算 | 在一致性成立后改善手感；需要快速精确恢复、逐帧重算、额外算力与状态缓冲 |

以约 60 帧/秒为例，预留 3 帧约为 50ms；这只是输入缓冲示例，不是端到端延迟承诺。具体帧率采用核心及制式的实际时间基准，不把所有 NES 游戏硬设为 60.000Hz。

回滚必须能够保存/恢复完整状态，并执行不呈现中间结果的单帧模拟。重算期间需抑制中间画面与重复音频；已经播放的声音不能简单撤回，音频策略也要验收。[GGPO 开发指南](https://github.com/pond3r/ggpo/blob/master/doc/DeveloperGuide.md)

这里参考回滚方法，不承诺直接引入原生 GGPO SDK 就能在微信 H5 中使用；浏览器运行、传输接口和三人支持都需独立集成验证。

## 4. 当前工程的可复用部分与缺口

| 部分 | 本地检查结果与设计要求 |
| --- | --- |
| 游戏库、资源加载、手机手柄 | 可以复用；手柄输出改为“本席位的输入采样”，交给同步层调度 |
| 多端输入 | `src/runtime-adapter.ts` 当前固定端口 0；需按固定席位注入所有端口，并在执行帧前设置完整输入 |
| 帧控制 | 当前能读帧号和暂停/继续；检查到的 `GameManager` 包装接口没有显式的精确执行一帧接口。浏览器 `requestAnimationFrame` 不等于模拟器一帧 |
| 状态恢复 | 当前 `restore()` 将恢复任务排队，再短暂运行主循环并异步确认，适合手动读档；不能直接充当高频、帧精确的回滚接口 |
| 确定性 | 单机存读档测试通过；尚未证明不同实例、不同 iPhone、恢复后重放具有一致结果 |
| 暂停/输入释放 | 单机失焦时立即暂停、清输入；联机必须通过同步协议统一处理，不能让某个客户端私自改变全局模拟输入 |
| 服务端 | 现有 Node/Docker/Caddy 可增加隔离的房间与输入转发服务；现有服务本身没有这些能力 |

源码检查范围为锁定的 EmulatorJS 4.2.3 `GameManager.js` 和本工程适配器，不能据此断言底层 Wasm 无法改造。需查清 RetroArch/FCEUmm 的执行与序列化入口，可能需要定制 Wasm 包装层或替换联机专用核心集成；先保持单机运行配置和存档兼容边界。

4.2.3 的旧联机分支要求实验开关；其 `postMainLoop` 附近仍有 `control syncing - broken` 注释。因此不能把打开开关视为完成联机。此前分析的 4.3.0-pre 音画传输路线也不等于这里的输入帧同步。[4.2.3 包装源码](https://github.com/EmulatorJS/EmulatorJS/blob/v4.2.3/data/src/GameManager.js)、[4.2.3 模拟器源码](https://github.com/EmulatorJS/EmulatorJS/blob/v4.2.3/data/src/emulator.js)

## 5. 三人拓扑与运行规则

三台手机各通过 WSS 连接同一个房间服务。客户端上传自己的逐帧输入；服务验证连接身份、固定席位、帧范围及速率，汇总并广播帧输入。首个原型服务器不运行模拟器、不生成音画，房主负责提供约定的初始快照；服务器维护房间与控制事件的顺序。完整已确认帧取各操作席位连续输入齐备的进度，不能简单用服务器墙钟判断。

首期采用 WSS 可复用现有域名与 TLS 入口，无须为这条传输路线配置 STUN/TURN。代价是 TCP 重传可能造成排队延迟，仍需弱网测试；后续若换 WebRTC DataChannel，则重新评估连接穿透与 TURN，不把“只传数据”当作无需中转的理由。

拟定协议至少包含 `protocolVersion / roomEpoch / seatGeneration / sequence / frame / buttons`；身份与席位以服务器绑定的连接为准。广播含完整帧输入；可批量/压缩传输，但需能恢复每一帧，不能只发送偶发按下/松开事件。服务端拒绝冲突的重复帧、越权席位和超窗口输入，限制快照与历史队列大小。

运行规则：

- 同一房间校验 ROM、核心构建、包装层、制式、设备配置及协议版本；禁用各端独立的作弊、快进和倒带。
- 本机显示菜单可保持同步循环继续运行；若菜单要求游戏暂停，由房间控制协议协调。切后台导致某台无法计算时，首个帧同步版本全局等待/暂停，不能沿用媒体方案“仅房主持续运行”的假设。
- 断线进入恢复屏障，保留固定席位；统一确认恢复帧、快照及后续输入后继续。首期恢复失败或超时结束房间，不让各端自行假设失联玩家的输入。
- 分歧时暂停并记录首个异常确认帧、配置与输入历史，再从指定快照恢复；重复分歧终止该局，不能靠不断覆盖存档掩盖不确定性。
- 首期仍不做房主迁移；手动读档/重开需结束当前房间后重新建房。恢复检查点与用户个人存档分开管理。
- 观众运行同一 ROM，接收快照和已确认输入，可适当落后播放；观众不贡献玩家输入，不应阻塞玩家的确认进度。

服务器只转发输入无法验证客户端是否篡改游戏结果；此阶段定位好友联机，不把一致性校验宣称为竞技防作弊。

三人操作仍要求 ROM 的模式支持至少三个玩家以及核心第三手柄通过验收。《赤色要塞》当前样本仍只能作为双人测试；“双人＋观战”可以有三位参与者。支持 1–4 人的候选 ROM 与验证要求见[多人方案](multiplayer-architecture-plan.md)。

## 6. 流量和设备成本

NES 每玩家 8 个按键的状态可压成 1 字节。以 60 帧/秒、3 个操作席位估算，单端接收的整组纯按键数据仅 `3 × 1 × 60 = 180 字节/秒`；这不是网络实测值，尚未包含帧号、鉴权/协议头、WSS/TLS、心跳、校验与重传。

工程预算可先按每端上下行各“几 KB/s 到几十 KB/s”估算，再以实际编码、批量策略和弱网数据修订。ROM/核心下载和首次、重连快照另计；不要把每帧完整状态上传后仍按按键流量计算。服务器按房间人数向各端分发，记录聚合流量才能估算容量。

相对音画流，每端网络负担有明显下降空间；每台设备却都需要稳定执行核心，回滚还增加 CPU 和内存使用。是否更省电以及可同时支持多少房间，需要实测，不能只从省流量推导。

## 7. 推荐验证顺序与停止条件

以下为确认时拟定的阶段与门槛。S0、S1 桌面核心验证、S2 和部分 S3 已完成；iOS 微信多机、真实三人游戏和回滚未验收，最新状态以实现文档为准。

| 阶段 | 工作与交付 | 通过门槛 |
| --- | --- | --- |
| S0 核心可控性 | 隔离验证精确逐帧执行、帧边界输入、完整状态保存/恢复；记录可用接口或定制构建方案 | 可重复控制执行帧数和恢复边界；回滚还需无中间音画输出的快速重算 |
| S1 一致性 | 多个隔离实例使用同一初始状态及固定输入记录；比较相同帧，加入恢复后重放 | 目标连续 20 分钟无已确认状态分歧；覆盖 iOS 微信多机，记录 ROM、设备与版本 |
| S2 双人到三人 | WSS 房间＋等待输入的帧同步；《赤色要塞》先验证双人，再用合适 ROM 验证第三手柄和三机 | 每端输入作用于正确席位；无独立进度；测量手感、输入延迟、等待占比、流量及帧率 |
| S3 弱网与恢复 | 延迟/抖动/丢包、切后台、断线、重连、成员退出、观战 | 稳定席位、无卡键、无静默分歧；等待和恢复状态用户可理解 |
| S4 回滚优化 | 仅在 S0–S3 基础稳定且延迟体验需要改善时，引入预测、历史快照和受限重放 | iPhone 持续游玩仍有算力余量；测量重放耗时、回滚次数/深度、音画副作用及耗电 |

状态比较要覆盖影响后续执行的真实模拟状态。先检查序列化内容是否混入无关填充或宿主计数；只有有依据地排除不影响模拟的字段，才能规范化摘要，不能随意忽略差异。原始状态、帧记录与回放用于诊断，现有单机存档测试不能替代本门槛。

S0/S1 失败时先定位包装层或核心问题，不直接堆房间 UI 或把更换网络协议当作修复。评估定制核心成本后再决定继续、替换联机适配，或回到媒体路线。S2 已可判断等待输入方案的实际手感；回滚不必与房间功能一起一次性开发。完成 S0/S1 前，不承诺完整联机交付工期。
