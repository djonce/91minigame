# 输入帧同步联机实现与验收

2026-09-18。已按确认的「不传音视频」路线完成测试版，并按追加授权推送 GitHub、部署 Docker。每端运行同一 ROM，服务端排序和转发输入，浏览器在本地生成画面与声音。当前线上版本为 `20260918-120949`（含 iOS 触控修复），入口为 [minigames.19ba.cn](https://minigames.19ba.cn/netplay.html?game=nes-chise-yaosai)。

## 使用方式

运行 `pnpm dev`，打开游戏库的「好友联机」，或直接进入 `/netplay.html?game=nes-chise-yaosai`。

1. 房主创建房间，复制邀请链接或房间号给朋友。
2. 朋友加入；第三位参与者玩《赤色要塞》时勾选「我来观战」。开局后暂不接受新成员。
3. 所有人点击「我准备好了」，房主点击「开始这一局」。准备按钮同时激活本机声音。
4. 房主在游戏本身的标题菜单选择 **2 PLAYERS**，再按 START。房间有两名玩家不会自动替 ROM 选择双人模式。
5. 各端只操作自己的固定席位。手机使用已优化的大画面和手柄，旋转屏幕保留同一局。
6. 玩家打开房间菜单或切后台会暂停全局，由房主「重新同步并继续」。断线重连后需再次点击准备，席位不变。

界面示例：[房间面板](screenshots/netplay-room.png)、[手机联机画面](screenshots/netplay-game.png)。

本地地址仅适合本机验证；两部手机应通过同一个 HTTPS 测试域名访问已发布的版本。不要把 `127.0.0.1` 邀请链接发给手机，也不要将普通局域网 HTTP 测试等同于微信 HTTPS 真机验收。服务器已更新，小程序默认指向正式域名；开发者工具重新编译本工程后可看到「好友联机（测试版）」入口。小程序发布和 iOS 多机验收未由服务器部署代替。

## 已实现的范围

| 能力 | 当前行为 |
| --- | --- |
| 传输 | 同域 `/netplay` WebSocket；HTTPS 下使用 WSS。没有音视频采集、编码、串流或 TURN 服务 |
| 房间 | 创建、邀请、加入、准备、开始、暂停、恢复、退出，最多三位参与者 |
| 玩家席位 | 协议预留 P1–P4；当前房间最多三人，席位固定，输入身份由服务端连接绑定 |
| 双人游戏 | 用户提供的《赤色要塞》按 ROM SHA 开放双人＋一位观战 |
| 三人操作 | Four Score 第三手柄及三端实际输入已用自制诊断 ROM 验证；真实三人游戏仍需逐 ROM 验收 |
| 同步 | 等待全部玩家输入的帧同步，预留 3 帧输入缓冲；慢设备、慢网会让全局等待 |
| 一致性 | 初始全状态屏障；每 120 帧比对完整序列化状态 SHA-256；不裁剪或忽略状态字段 |
| 恢复 | 房主提供完整快照，全部客户端恢复并校验后继续；重连补齐已提交的帧，最多保留最近 240 帧 |
| 观战 | 自己运行核心、接收相同输入；不提供玩家输入，不参与游玩中的哈希屏障；状态分歧会退出观战 |
| 生命周期 | 断线席位保留 30 秒；房主主动退出结束房间；没有房主迁移、刷新页面恢复和中途新加入 |
| 保护 | 消息体、快照、队列、帧窗口、消息速率、房间数和连接数限制；同源检查、随机凭据和重连令牌轮换 |

快照只在开始和重新同步时传送；游玩期间传按键、帧号、检查点摘要和房间事件。连接信息显示应用数据累计字节，尚未统计 TLS/TCP 开销。每个新设备仍需下载 ROM 与核心，这部分不计入对战消息。

联机页没有个人存档、快进、作弊和倒带入口，不会写入单机存档。首期没有预测回滚或竞技防作弊。服务器不运行模拟器，不能证明客户端未篡改游戏。

## 核心与代码边界

- `shared/netplay.ts`：协议、固定输入位序、消息类型和窗口常量。
- `server/netplay-rooms.ts`：房间状态机、席位权限、帧汇总、屏障与恢复。
- `server/netplay.ts`：WebSocket 接入、来源检查、限额、心跳和资源回收。
- `src/netplay/runtime.ts`：锁定核心的精确逐帧适配、快照和恢复。
- `src/netplay/client.ts`：按序执行消息、本席位输入、校验和重连。
- `src/netplay/page.ts`、`netplay.html`：房间界面，复用现有手机画面和手柄。

运行时仍为 EmulatorJS **4.2.3**、FCEUmm legacy 单线程核心。核心归档 SHA-256 为 `f1054b094e7149fd6278485bc1b2e51ff75c5259048ddb1134171e53d651f239`。联机适配先校验解压后的 JS glue SHA `dba07936f4502e66cd1d31adfcea8102664c3c6d8fd947bf3c151a3c93e5e73c`，只在内存中添加一个受控执行入口；下载归档保持原样。核心更新必须重新验证，不能只改版本号。

该构建使用 Asyncify。每帧必须等待其异步执行完成，且最终再次暂停 Emscripten 调度，否则网络等待期间核心会自行继续运行。现在每帧校验原始计数恰好增加 1，等待期间不得推进，避免以浏览器回调次数冒充模拟器帧数。

Four Score 不能只写 RetroArch 配置项：此构建需通过 `--device 3:513 --device 4:513` 设置实际端口；双手柄模式显式断开 P3/P4。配置分别进入联机 profile，不能混用。状态序列化产生的 WASM 堆缓冲在复制后释放，避免高频校验沿用上游 UI 保存辅助函数时泄漏内存。

## 登记三人候选 ROM

`pnpm rom:add` 后，可由维护者在 `.local/games.json` 对相应条目增加：

```json
{
  "id": "three-player-game",
  "title": "已准备验证的三人游戏",
  "path": "/absolute/path/to/game.nes",
  "netplay": {
    "sha256": "填写该 ROM 的 64 位小写 SHA-256",
    "players": 3,
    "controller": "nes-four-score",
    "fps": 60.0988
  }
}
```

SHA 必须匹配文件，替换 ROM 后不会继承旧联机能力。`players` 描述模式的操作人数，不会修改 ROM 的角色数量。三人以上必须使用 `nes-four-score`，其他主机或不同扩展手柄暂不支持。`fps` 是配置元数据，实际节奏由锁定核心运行；当前验证样本为 NTSC，PAL 虽可登记但尚未验收。

自制诊断 ROM 在 `tests/controller-rom.ts` 通过原始 6502 指令生成，只用于测试，不作为游戏条目公开，也没有提交商业 ROM。

| --- | --- |
| 类型检查、H5/Node/小程序构建 | 通过 `pnpm check`、`pnpm build` |
| 单元测试 | 18 项通过，包含原始 ROM 摘要、三席位、越权输入、快照损坏、分歧、重连和退出 |
| 浏览器及生产回归 | 9 项浏览器测试、2 项生产测试通过；单机存读档、手机多指/旋转和错误路径保持正常 |

| 精确逐帧及恢复 | 240 帧执行后恢复初态，重放完整状态相同；等待期间帧数不变 |

| 双人＋观战生产构建 | 实际《赤色要塞》ROM，暂停/恢复、房主与来宾重连、席位不变、房主退出结束房间 |

长测完成后增加了 P3 设备显式配置与快照缓冲释放，再运行核心恢复、P3 和房间集成回归；该长测不是最终源码另做的一次 20 分钟全网络测试。它验证逐帧核心一致性，不替代真实网络和多机验收。

## 部署和待验收项

Dockerfile 已增加固定版本 `ws` 运行依赖；原有 Caddy 反向代理可承载 WebSocket 升级，无需媒体端口或 TURN。可通过 `NETPLAY_ORIGIN=https://minigames.19ba.cn` 限定握手来源。2026-09-18 已在阿里云服务器完成实际 Docker 镜像构建及健康检查，46 个运行文件校验通过，镜像中的 `ws` 为 8.21.3。发布与回滚见[部署记录](deployment.md)。

后续必须用两到三台 iOS 微信设备验收：持续游玩与声音、多指触控、横竖屏、Wi-Fi/蜂窝交叉、锁屏/切后台、断线后准备与恢复、发热和耗电。现有单机 iOS 真机测试结果不覆盖联机。

真实三人游戏仍需提供支持三人同时操作且使用适配手柄协议的 ROM，核实游戏模式及长期一致性。受限于等待输入方案，网络差时会停顿；是否引入预测回滚应在真机实测输入延迟和算力余量后决定，符合原方案 S4 的条件开发顺序。
