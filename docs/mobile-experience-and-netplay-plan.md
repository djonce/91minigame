# 手机游戏交互优化与双人联机调研方案

日期：2026-09-18。状态：**待确认，尚未实施**。

后续状态：用户已确认“先开发手机界面优化”。阶段 A 已在本地实现，见 [实现与验收记录](mobile-ui-implementation.md)；B/C 联机部分未获本轮确认，仍保留为规划。以下内容保留为原调研基线。

用户已反馈真机功能正常，测试平台为 iOS；具体机型、iOS 与微信版本尚未提供。本轮只研究、设计和规划，不修改播放器业务代码、模拟器版本或线上部署。

## 1. 建议确认的方向

1. **先优化手机游玩体验**：横屏优先、竖屏完整可用；画面等比放大、放大手柄、把存档和设置收进暂停菜单。
2. **联机先做隔离验证**：以两位好友玩同一款支持双人同屏的 NES 游戏为首期目标，优先验证 iOS 微信 × iOS 微信。
3. 单机继续保留已验证的 EmulatorJS 4.2.3；联机先用配套的官方预发布客户端与服务端做验证，通过门槛后再决定正式接入。不同核心的存档分开保存。

结论：双人联机有可行的技术路线，但目前不能承诺该路线已在 iOS 微信里稳定可用。单机真机通过，并不能证明画面采集、音频传输、WebRTC、跨运营商连接都通过。

## 2. 当前手机界面为什么显得小

根据 `player.html`、`src/player.css`、`src/player.ts` 和现有验收截图：

| 现状 | 影响 |
| --- | --- |
| 小程序原生导航之外，还有 64px H5 标题栏 | 重复占用竖向空间 |
| 外层左右各 16px，屏幕壳左右各 11px，再加边框 | 390px 宽的 H5 视口，游戏区域约只剩 334px 宽 |
| 屏幕上方 32px 状态条、下方 25px 装饰条 | 实际画面占比进一步下降 |
| 暂停、快存、读档、声音、重开常驻一行 | 游戏与操作区之间隔了一层低频操作 |
| 竖屏方向盘 108×108px，单格 36×36px；A/B 各 48px | 方向键触控偏小，滑动转向不方便 |
| 存档面板直接接在手柄下方 | 播放页需要滚动，游玩时容易误滚 |
| 横屏保留固定 160px 侧边空白，并限制 `100vh - 150px` 的画面高度 | 尺寸依赖经验常量，部分手机无法充分利用高度 |
| 输入绑定四个独立方向按钮，未按手指移动位置重新计算方向 | 按住后滑向另一个方向，不等同于真正的方向盘操作 |

## 3. 新交互设计

### 3.1 横屏：作为主要游玩姿势

- 使用横向三块区域：**左侧方向盘／中央完整游戏画面／右侧 A、B 键**。
- 中央画面在剩余区域内按 4:3 最大化显示，保留 NES 原有画面比例；不拉伸、不裁掉 HUD、默认不让手指覆盖游戏。
- 左右操作区参考宽度各 144–160px，按实际视口和安全区调整；过窄的横屏进入紧凑尺寸，不强行挤压画面。
- 暂停/菜单位于侧边操作区上方，SELECT/START 放在较低的位置。存档、读档、重开、设置不再常驻画面下方。
- 打开菜单时单机暂停并释放按键；关闭菜单后由用户点击继续。联机时使用第 6 节的房主控制规则。
- 微信原生导航和胶囊保留平台实际行为，界面示意中的尺寸指 **H5 可用区域**，不是承诺消除所有微信系统界面。

### 3.2 竖屏：上方大画面，下方大手柄

- 页面内只保留简短的状态/菜单入口；在小程序内收起重复的 H5 返回栏与大标题。
- 游戏画面两侧仅留约 8px；去掉厚屏幕壳、装饰条和多余纵向留白。
- 方向盘与 A/B 分别位于下方左右；SELECT/START 单独排在容易够到的位置，避免被挤成小按钮。
- 游戏与手柄在一屏内完整可见；只允许暂停菜单内部滚动。
- 首次可提示横屏体验更好，但竖屏可以直接开始；不把旋转手机设为必经步骤。

### 3.3 手柄与菜单细节

| 控件/行为 | 设计目标 |
| --- | --- |
| 方向盘 | 默认约 144–156px；连续触控面，按坐标划分八方向，斜向同时触发两个方向 |
| 方向中心 | 小死区，约总尺寸的 8%–12%，真机调整 |
| A/B | 可见直径约 64–72px；触控区域不小于可见范围，邻键热区不重叠 |
| SELECT/START | 有效触控高度至少 44 CSS px，按下反馈清晰 |
| 多点触控 | 方向+A、方向+B、A+B 均可同时保持；手指之间独立跟踪 |
| 按键释放 | 抬手、触控取消、失焦、打开菜单、切换布局都释放，避免“卡住方向” |
| 暂停菜单 | 继续、快速存档、存档槽/读取、声音、按键大小、重新开始、返回游戏库 |
| 存档 | 沿用现有快存+3个手动槽及导入/导出；读档/重开需明确操作，减少误触 |
| 可调选项 | 首期提供标准/大号按键、左右手布局、音量；记住当前设备选择 |
| 暂缓项 | 自由拖拽每个按键、连发/宏、震动依赖、皮肤商店 |

44px 是本方案的最低触控目标，主要操作按键会更大；实际尺寸以 CSS 像素和真机触达感受验证。

### 3.4 屏幕利用率：给出可验证的预期

以下是按当前 CSS 和新布局几何关系计算的**规划估算**，不是改版后的实测值。视口均指 H5 能使用的区域，微信栏和安全区不能重复算入。

| 对比条件 | 当前估算 | 新方案目标 | 解释 |
| --- | --- | --- | --- |
| 竖屏可用宽度 390px，4:3 | 334×251px | 374×281px | 画面宽度增加约 12%，面积增加约 25% |
| 横屏可用区域 844×390px，4:3 | 约 320×240px¹ | 约 499×374px² | 面积约为原来的 2.4 倍 |
| 方向盘 | 108px | 144–156px | 单格由约 36px 增至约 48–52px |
| A/B | 48px | 64–72px | 可见直径增加约 33%–50% |

¹ 当前横屏最大高度为 240px，若渲染器按 4:3 等比装入，实际画面宽约 320px。

² 示例扣除外边距 8px、左右操作区各 148px、间隔各 12px。若实际微信视口更矮、有刘海安全区或系统导航，尺寸相应降低，不能直接照搬此数字。

竖屏受屏幕宽度和 4:3 比例限制，不适合承诺画面放大一倍。显著提升画面面积主要依靠横屏；竖屏的主要改善是更大按键、紧凑布局和无需滚动。

### 3.5 iOS 微信的实现边界

- 官方 `web-view` 文档明确：`navigationStyle: custom` 对该组件无效。因此不能把“去掉微信顶部导航”作为核心收益，也不能承诺通过 CSS 获得整机全屏。[微信 web-view 文档](https://developers.weixin.qq.com/miniprogram/dev/component/web-view.html)
- 播放页拟配置 `pageOrientation: auto`，先验证手机旋转时原生容器与 H5 都正确变化；若目标版本自动旋转不符合预期，再评估独立横屏入口。页面配置支持 auto/portrait/landscape，但具体 iOS 微信版本仍需实测。[微信页面配置](https://developers.weixin.qq.com/miniprogram/dev/reference/configuration/page.html)
- 使用实际视口宽高、`visualViewport`/resize 和 CSS 尺寸计算；优先动态视口单位并提供回退。避让 `safe-area-inset-*` 和 Home 指示条，不依赖 `100vh` 的固定高度判断。[WebKit 安全区说明](https://webkit.org/blog/7929/designing-websites-for-iphone-x/)
- 横竖屏只改变布局，不销毁模拟器、不重新加载 ROM。继续使用已修复的暂停截图策略，避免旋转后黑屏。
- H5 的 Fullscreen API、方向锁定只能作为探测通过后的附加能力；核心体验依靠微信页配置和自适应布局，不能以 iPhone Safari 的结果替代微信验证。
- 游戏手柄留在 H5 内。官方 `postMessage` 消息在后退、销毁、分享等特定时机交付，不用它跨原生与 H5 传实时按键。[微信 web-view 通信说明](https://developers.weixin.qq.com/miniprogram/dev/component/web-view.html)

### 4.2 新版联机实际上如何工作

已阅读 `v4.3.0-pre/data/src/netplay.js`：房主采集 Canvas 和模拟器音频，WebRTC 发给来宾；来宾通过 DataChannel 将手柄输入回传，房主注入对应玩家端口。信令服务器管理房间并交换连接信息。

这属于**房主串流**，不是双方同时运行模拟器后做确定性帧同步，也不是把 ROM 放在云服务器里执行。源码默认采集 30fps，不能承诺来宾能看到与本机 60fps 相同的效果。来宾没有持续模拟的必要，但上游集成路径可能仍先加载 ROM/初始化核心，内存与启动成本要验证。[固定版本联机源码](https://github.com/EmulatorJS/EmulatorJS/blob/v4.3.0-pre/data/src/netplay.js)

实际使用形态：房主控制 1P，好友控制 2P，两人看同一个游戏画面。首个候选是现有《赤色要塞》样本，但要先验证该 ROM 的双人模式、第二手柄映射和同时游玩；不能因为格式是 NES 就自动标记为支持联机。当前页面写死的“单人”也要改为经验证的游戏能力元数据。

### 4.3 技术路线比较

| 路线 | 适用性 | 主要代价 | 建议 |
| --- | --- | --- | --- |
| 官方 4.3.0-pre 房主串流 | 已有客户端和服务端，可最快核实可行性 | 预发布、核心变化、iOS 捕获/播放、房主性能与网络 | **首选隔离验证** |
| 保留 4.2.3，自建房主串流适配层 | 可保留现有单机核心与存档 | 要维护音频捕获、信令、重连与输入协议 | 若新版回归代价太高，作为第二选择；仍需 WebRTC 真机验证 |
| 双端模拟＋帧同步/回滚 | 带宽较小，画面由各端本地生成 | 确定性、逐帧控制、迟到输入、回滚、状态校验；不是简单转发按键 | 首期不做 |
| 云服务器模拟＋串流 | 不依赖手机充当房主 | 每房间算力、媒体编码、调度、资源隔离、持续带宽 | 当前阶段不采用 |

如果 iOS 微信 WebRTC 媒体链路不能通过测试，自建同样依赖 WebRTC 的串流不会自动解决问题。届时应先报告具体不兼容点，再评估双端模拟路线或产品入口调整，不能直接以 WebSocket 转发按键替代同步方案。

## 5. 联机需要增加的服务

拟复用现有阿里云 Docker 和 Caddy，新增隔离的房间/信令服务及 coturn；本次未创建这些服务。

- **房间/信令**：创建、加入、准备、玩家席位、连接协商、心跳和退出。HTTPS/WSS 通过 Caddy；房间状态先用有界内存，重启关闭房间，首期无需数据库或 Redis。
- **STUN/TURN**：尽量点对点直连，蜂窝网络或 NAT 穿透失败时走 TURN。测试必须包含强制 relay，不能仅凭同一 Wi-Fi 成功验收。[coturn 官方说明](https://github.com/coturn/coturn)
- **TURN 网络**：另行核实可用端口、阿里云安全组和公网映射；规划 3478 TCP/UDP、5349 TLS 与受限 UDP relay 端口范围。普通 Caddy HTTP 反代不能代替 TURN 数据通道；如需 TURN-over-TLS 443，再单独评估端口/IP 分配。
- **访问控制**：房间人数限制、短期入房凭据、创建/加入限流、超时清理；TURN 使用短期凭据，不把长期密钥写入前端。对 DataChannel 输入绑定玩家身份、校验按键和频率，断线释放该玩家的所有按键。
- **资源绑定**：同房间绑定 ROM SHA-256、运行配置、核心摘要、联机协议版本；数字游戏 ID 持久化分配，不由每次启动随机生成。

不直接使用示例里的免费公共 TURN 或 Google STUN 作为生产唯一依赖。

带宽按假设估算：每位来宾 1–2Mbps 媒体流，单向约 0.45–0.90GB/小时，另加音频与协议开销；一位来宾的 TURN 中转需要相近的入口和出口吞吐。十个双人房间若全部中转，约需 10–20Mbps 出口媒体带宽，尚未计算余量。这不是现有服务器容量或报价，需根据实测码率和已购带宽确认。

## 6. 双人房间的最小产品范围

1. 选择已验证支持双人的游戏 → 创建好友房间。
2. 房主复制房间码或分享小程序邀请；首版即使分享能力未完成，房间码也能加入。
3. 好友加入为 2P → 双方点击准备以激活声音 → 房主在 ROM 中选择双人模式并开始。
4. 游玩时只显示简短的玩家、连接和必要延迟提示，不展示调试日志或协议参数。
5. 初版限两人，不做匹配大厅、观战、语音聊天、排行榜或云存档。

**存档规则**：首版联机房间只由房主保存；房内禁用读档和重开，避免突然改变双方进度。需要恢复既有存档时，由房主在开房前处理，并验证运行版本匹配。来宾不能把自己的本地存档当成房间权威状态。

**暂停规则**：房主菜单可暂停全局并通知好友；好友菜单只释放自己的输入、显示菜单，不擅自暂停房主。不要沿用现有单机 `blur → pause` 而不区分联机角色。

**断线规则**：掉线立即释放按键并显示原因，允许在短时间窗口内尝试恢复；恢复失败退出房间。房主锁屏、切后台或离开后，首版不做房主迁移、不保证后台持续运行。能发送暂停提示时发送，网络已断时显示连接中断。

**分享边界**：小程序邀请需携带房间入口并考虑短期票据过期；H5 `postMessage` 仅用于允许的分享/导航数据，不参与游戏同步。

## 7. 先验证，再决定是否接入

| 验证项 | 验收目标/处理 |
| --- | --- |
| iOS 微信基础能力 | 实际验证 RTCPeerConnection、DataChannel、Canvas captureStream、WebAudio→MediaStream 与远端音频/视频；不能只检查 API 名称存在 |
| 双 iPhone 同网 | 房主、来宾互换；确认 1P/2P 分工和双人模式真正可玩 |
| 跨网络 | Wi-Fi↔蜂窝、不同运营商；分别确认直连和强制 TURN 路径 |
| 持续运行 | 每个关键组合至少 20 分钟；观察音画、发热、帧率、内存、黑屏和断线 |
| 延迟 | 记录 RTT、丢包、实际按键到画面变化延迟；建议正常测试网络 p95 操作响应≤150ms 为可玩目标，>200ms 明显降级并重新评估；这些是验收目标，不是已达成值 |
| 视频流 | 源码默认 30fps；目标稳定接收、不持续掉帧，后续再评估更高帧率及耗电 |
| 生命周期 | 打开菜单、分享后返回、切后台、锁屏、电话打断、网络切换后均无卡键；恢复/结束行为清楚 |
| 存档隔离 | 单机旧存档完整保留；新核心存档另设运行配置 ID，禁止未经验证互读 |
| 失败降级 | 单机始终可用；能力不足时明确提示联机暂不可用，不假报已连接 |

用户目前仅确认 iOS，手机型号和系统/微信版本在实施前记录。Safari 可作为诊断对照，但不能作为微信联机通过的证明。
