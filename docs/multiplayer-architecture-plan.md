# 多人联机方案细化：三人场景与四席位扩展

日期：2026-09-18。本文为早期媒体路线调研存档，基于 `f85b71e` 和锁定的 EmulatorJS 候选源码分析。用户随后确认输入帧同步路线，当前实现见[联机实现与验收](input-sync-netplay-implementation.md)；下文不作为当前代码能力描述。

后续补充：用户提出“只同步事件和进度，不传音视频”。新增[输入帧同步方案](input-sync-netplay-plan.md)，建议先验证该路线的逐帧控制与多端一致性。本文件的房间容量、游戏人数和固定席位设计可复用；音画拓扑、带宽、后台行为及工期仅适用于原媒体路线，不作为新路线的实现要求。

## 1. 结论与范围

**现有工程适合增量扩展三人联机，但当前代码还不支持联机；三人能否各控一个角色，还取决于游戏模式、核心输入设备和 iOS 媒体链路。**

本方案按“三人各自操作一个角色”作为主要验证目标，同时设计“二人操作＋一人观战/轮换”。房间与输入协议按最多四个玩家席位设计，首个联机测试版先限制三位参与者，不能把预留四席位称为四人已通过验收。

| 场景 | 判断 | 开放条件 |
| --- | --- | --- |
| 三人进入同一个房间 | 可以设计实现 | 房间服务、身份、容量与连接状态管理 |
| 三人同时操作不同角色 | 路线可行，有游戏限制 | 游戏该模式支持至少三人；核心正确配置第三手柄；三台手机通过验收 |
| 《赤色要塞》三人同时操作 | 当前样本不开放 | 已看到菜单只有 1 PLAYER / 2 PLAYERS；增加网络席位不会给游戏增加第三角色 |
| 《赤色要塞》二人操作＋一人观战 | 可以扩展 | 增加只读观战身份；仍需三端媒体与真正双人模式验证 |
| 第三人与 2P 轮换 | 可以另加交接功能 | 暂停后由房主确认移交，撤销旧输入权限再发新权限；不叫三人同时玩 |
| 三人分别玩不同进度 | 不属于本方案 | 这里共享同一局游戏、同一画面，不是三个独立关卡 |

三人并不要求原生游戏“有网络功能”：房主运行一次模拟器，三人的输入映射到其不同手柄端口。不能用这条路线为单人/双人游戏凭空增加玩家角色。

## 2. 当前架构支持到哪一层

| 层次 | 当前实现 | 多人所需变化 |
| --- | --- | --- |
| 小程序与 H5 | web-view 打开独立播放器；手机手柄已改版 | 保留入口与大手柄，新增房间入口、自己的玩家号和连接状态 |
| 手柄输入 | `src/gamepad.ts` 合并本机触控/键盘来源 | 复用本地手柄；输出送到当前席位对应的本地或远端通道 |
| 核心适配 | `RuntimeAdapter.input()` 固定调用 `simulateInput(0, ...)`；只维护一个 active 集合 | 支持指定端口、按席位维护按下状态和单独释放，区分原始核心输入与网络发送 |
| 游戏清单 | `Game` 只有 NES/摘要/运行配置等，无多人能力 | 增加模式、同时玩家数、设备配置和已验证状态，不能只加 `multiplayer: true` |
| 生命周期/菜单 | 任意失焦会暂停本机模拟器；本机保存/恢复 | 区分房主、来宾、观战；好友切后台不应调用房主的全局暂停 |
| 服务端 | 游戏目录、ROM、运行资源的只读 API | 新增房间/信令服务及短期加入凭据，不把媒体混进 ROM 下载 API |
| 部署 | Docker 应用＋Caddy | 增加隔离的联机服务和 TURN，保留现有应用路由 |

这属于增加联机层和扩展核心适配，不需要重写游戏库、ROM 校验或手机手柄。存档仍按 ROM 摘要与运行配置隔离。

## 3. 上游证据及不能直接照搬的部分

### 3.1 已核实的能力

- 本轮评估的 EmulatorJS `v4.3.0-pre` 为预发布版本，包含 WebRTC 联机；当前稳定单机仍锁定 4.2.3，两套核心不可随意互换。[发布说明](https://github.com/EmulatorJS/EmulatorJS/releases/tag/v4.3.0-pre)
- 候选客户端初始化 `maxPlayers = 4`，为每位来宾创建独立连接；候选房间服务端接收容量字段，默认值为 4。这证明并非只为两端编写，不等于本工程已有四人功能。[客户端固定版本](https://github.com/EmulatorJS/EmulatorJS/blob/v4.3.0-pre/data/src/netplay.js)、[服务端候选提交](https://github.com/EmulatorJS/EmulatorJS-Netplay/blob/4090ca7bda795a8b7a7596f4d41a4605b515d9c5/src/main.rs)
- FCEUmm 官方文档描述 NES/Famicom 多手柄游戏最高四人，包含 User 3/4 和扩展设备配置。文档中的 User 5 是扩展设备配置位置，不表示五个可玩角色。[FCEUmm 多手柄说明](https://docs.libretro.com/library/fceumm/#multitap-support)
- 有可选择的三至四人 NES 游戏：开发者说明《Micro Mages》支持 1–4 人同时游玩，并提供 NES ROM。它可作为后续候选样本；本次没有获取、运行或验证该 ROM。[开发者页面](https://morphcatgames.itch.io/micromages)

官方核心文档描述的是核心能力，不能直接证明项目锁定的 Wasm 包装层已经正确暴露第三/第四手柄或设备切换。需要用具体 ROM＋具体核心版本实际验证。

### 3.2 源码审查后新增的设计要求

1. **席位显式分配**：候选客户端 `getUserIndex()` 使用 `Object.keys(players)` 的位置。成员增减或服务端序列化顺序变化时有改号风险。用服务器分配的固定席位替代这一推算。
2. **输入权限绑定连接**：候选接收路径使用消息里的 `player/index/value` 注入核心。正式接入应由房主按已认证连接查席位，不能信任来宾自报的端口号。
3. **房主退出规则统一**：候选服务端有转交 owner 的分支；但房间 owner 改变不能迁移房主的模拟器状态。首期房主离开结束房间，不能仅重命名 owner 就继续。
4. **观战单独建模**：现有候选协议以玩家列表为主。观战要有独立权限、席位为空、禁止注入输入，不能把观众伪装成多出来的第三手柄。

以上是代码层面的风险判断，尚未完成多设备复现或联调。正式版本不能只修改 `maxPlayers` 就上线。

## 4. 推荐拓扑：一个房主，两个来宾

| 通道 | 三人房间中的工作方式 |
| --- | --- |
| 房间/信令 | 三台设备都通过 HTTPS/WSS 连接联机服务，用于加入、准备、席位、连接协商、暂停和退出 |
| 游戏执行 | 仅房主持续运行核心；房主操作 P1，两个好友操作 P2/P3 |
| 音画 | 房主分别向好友甲、好友乙发送同一局画面与游戏声音 |
| 按键 | 甲/乙各自经 DataChannel 回传输入，房主映射到固定手柄端口 |
| 穿透失败 | 对失败的那条连接使用 TURN 中转；另一个好友仍可直连 |
| 来宾之间 | 不互相转发音画或输入，避免第三端成为额外中转节点 |

这是星形连接。三人有两条房主到来宾链路；四人会有三条。复用同一采集源不意味着浏览器只做一次编码或只上传一份数据，需要测房主端的编码、发热和电量。

上游初始视频设置为 30fps、每连接约 1.8Mbps 上限，并可能调整码率。来宾的流播放、声音解锁和手柄在我们的 H5 内整合；不通过小程序 `postMessage` 传高频游戏输入。

**推荐取舍**：用固定版本上游做隔离的媒体/核心验证；正式产品由我们维护房间规则、稳定席位及输入权限。房间服务优先延续项目的 Node.js/TypeScript 技术栈并验证 Socket.IO 协议兼容，Rust 示例作为参考与对照，不混搭未经验证的分支。

如果预发布核心回归代价过高，可以评估在 4.2.3 上单独加媒体适配，但仍需验证 iOS WebRTC 与第三手柄能力，不会自动绕开这些限制。

## 5. 人数、席位与游戏能力模型

### 5.1 三个不同的容量

- `maxParticipants`：在线参与者总数，含房主、玩家、观众；首期三人。
- `playerCapacity`：实际可操作席位数，取游戏模式、已验证核心端口和产品上限的共同约束。
- `spectatorCapacity`：允许的观众数，仍受参与者总数和媒体负载限制。

举例：三人合作房间为 3 操作席位、0 观众；《赤色要塞》三人房间最多是 2 操作席位、1 观众。观众不消耗手柄端口，却同样消耗一条下行媒体流。

### 5.2 游戏与运行配置

| 字段 | 用途 |
| --- | --- |
| `modeId`、`playMode` | 区分合作/对战/轮流；同一个 ROM 的故事模式和对战模式可能人数不同 |
| `simultaneousPlayers` | 经验证可用的人数集合，例如候选游戏测试后才允许 `[1,2,3,4]` |
| `controllerProfileId` | 普通双手柄、Four Score/Famicom 扩展等固定配置；不能只根据 `.nes` 扩展名推断 |
| `runtimeProfileId`、核心摘要、ROM 摘要 | 绑定同一局的确切游戏和运行环境 |
| `netplayProtocolVersion` | 固定本项目输入、席位和控制消息的协议版本 |
| `validationStatus` / 验收记录 | 未测试、仅本地多手柄通过、指定设备联机通过分别记录 |

第三手柄未通过时，即便房间连接三人，也不能显示“三人合作已支持”。游戏不支持时给出“本模式最多 2 人，可选择观战或更换游戏”。

### 5.3 稳定席位

- 预留 `seats[0..3]`，对应显示的 P1–P4；成员 ID、连接 ID、席位和房主身份分别保存。
- 房主首期固定 P1。P2 掉线时 P3 仍保持 P3，不向前补位。
- 短暂断线保留席位约 15 秒；超时释放，但不改变其余玩家的手柄映射。具体时间作为可调参数真机验证。
- 重连凭据绑定房间、成员和会话代数；重新接入后增加输入代数，丢弃旧连接的迟到消息。
- 观战转操作/轮换只允许在房主确认的暂停状态下进行：撤销旧权限、释放该席位、双方确认、新代数生效后继续。首期不实现房主迁移。

## 6. 输入、暂停与存档边界

拟将适配器扩展为 `input(port, button, down)` 和 `releasePlayer(port)`，保留 `releaseAll()` 用于全局暂停/结束。这个接口是设计，当前代码没有更改。

| 事件 | 房主/服务端处理 |
| --- | --- |
| 来宾按键 | 校验所属房间和已分配席位，只处理白名单 NES 按键；拒绝自报其他玩家端口 |
| 多来源同时按键 | 每个席位独立聚合，放开 P2 的 A 不影响 P1/P3 的 A |
| 断线或输入心跳失效 | 单独释放失联席位；对另外两位提示，不清空其他玩家按键 |
| 来宾打开菜单/切后台 | 释放来宾输入，关闭其本地操作；不自动暂停房主模拟器 |
| 房主打开菜单/切后台 | 全局暂停、释放全部输入并通知所有来宾；不能保证 iOS 后台继续推流 |
| 房主退出/长期失联 | 结束本房间；向来宾说明原因并返回房间入口 |
| 存档 | 仅房主保存；不同核心配置继续分开保存 |
| 读取/重开 | 首版房内禁用。房主先退出房间恢复进度，再创建新房间 |

输入消息包含序号、会话/席位代数和完整按键状态，并在状态变化时立即发送、按约 20–30Hz 补发状态，避免仅依赖一次“抬起”事件。接收端拒绝旧代数、过期或乱序状态；输入超时的释放阈值初始评估约 500ms，实际按网络测试调优。

上游采用可靠有序 DataChannel；验证阶段需比较其在丢包下的排队延迟，与“无序、有限重传/不重传＋完整状态补发”的方案。普通按键与可靠的房间控制消息分开，测完再锁定传输参数。两者都不是确定性帧同步或回滚。

房主的监听音量与采集送出的音量需拆分，避免房主静音导致所有好友无声；来宾和观战者只控制自己的播放音量。需验证新版音频接口，不能直接复用现有单机静音逻辑。

## 7. 带宽和服务器选择

以下按每个远端接收者 **1–2Mbps 视频**估算，音频与协议开销另计；不是手机或服务器的实测容量。

| 房间参与者 | 房主远端接收者 | 房主总上行 | 全部走 TURN 时服务器出口 | TURN 单向媒体流量/小时 |
| --- | --- | --- | --- | --- |
| 2 人 | 1 | 1–2Mbps | 1–2Mbps | 0.45–0.90GB |
| 3 人 | 2 | 2–4Mbps | 2–4Mbps | 0.90–1.80GB |
| 4 人 | 3 | 3–6Mbps | 3–6Mbps | 1.35–2.70GB |

TURN 同时有相近的入口流量；表格只列出口。三人房间有一位观众时，其媒体成本与三人都操作接近。十个三人房间若全部中转，仅视频出口约 20–40Mbps，还需要余量；不能以当前应用容器的 `1 CPU / 512MiB` 推断整台机器能承载多少房间。

服务器新增服务建议：

1. **netplay**：独立 Docker 服务，管理房间、固定席位、临时凭据、心跳、容量与协商。Caddy 提供 HTTPS/WSS，同源路径与现有 API 区分；默认单实例、有界内存，重启明确结束房间。
2. **coturn**：独立运行，短期凭据、带宽/分配数量限制；核实 3478、5349 和受控 relay 端口范围及阿里云安全组。Caddy 的普通 HTTP 反代不承担这部分媒体转发。[TURN 工作方式](https://webrtc.org/getting-started/turn-server)
3. **现有 app**：继续提供目录、ROM、运行资源；联机服务故障不妨碍单机。

本轮没有登录服务器核实公网带宽，也没有开端口或部署。实施时再核对已购带宽、可用 CPU/内存及与现有容器的隔离。

### 何时考虑 SFU

三人先验证房主直发两路。若中低端 iPhone 发热或蜂窝上行成为瓶颈，再评估 SFU：房主上传一份媒体，服务器转发给两位好友。它增加一段服务器路径、运维和客户端接入工作，不能只更换 TURN 地址就获得。[SFU 架构说明](https://mediasoup.org/documentation/overview/)

SFU 不修复 ROM 人数限制，也不能保证修复 iOS Canvas/音频采集不兼容；若采集本身失败，需要先改变客户端技术路线。首期不引入云服务器运行模拟器、帧同步/回滚或无限观战。

## 8. 验证顺序与放行门槛

| 阶段 | 要回答的问题 | 放行门槛 |
| --- | --- | --- |
| B0：本机多手柄 | 具体 ROM 的第三角色真能单独操作吗？ | 锁定 ROM/核心/设备配置，三个输入端口各自控制对应角色，组合按键和释放互不串扰 |
| B1：双机媒体 | iOS 微信音画、手柄往返和 TURN 可用吗？ | 实际播放与操作通过，不能以 API 存在或 Safari 成功代替 |
| B2：三机负载 | 一个 iPhone 房主能稳定服务两位好友吗？ | 三台设备同时操作至少 20 分钟，房主角色互换；直连、单路 TURN、两路 TURN 均有记录 |
| B3：成员变化 | 退出、重连、轮换会不会控制错角色？ | P2 退出后 P3 不改号；重连不吃旧按键；观众注入输入被拒绝；房主退出全房一致结束 |
| C：产品接入 | 用户能创建、加入、准备和恢复连接吗？ | B 阶段通过后接房间 UI、邀请码/分享、状态反馈及上线验收 |

新增三人测试组合至少覆盖：三台 iPhone 同 Wi-Fi；房主 Wi-Fi、两个来宾分别蜂窝；房主蜂窝上行；不同运营商；限制其中一个来宾下行，确认另一人可继续。记录手机型号、iOS、微信版本以及实际 ICE candidate-pair，不用候选列表里出现 relay 代替实际走 TURN 的证据。

建议指标：正常测试网络下远端按键到画面响应 p95≤150ms 为目标，持续 >200ms 需降级/重新评估；记录实际接收帧率、停顿、丢帧、房主推流开销和发热。RTT 不能代替完整的操作到画面延迟。默认验证 30fps 远端视频，不承诺来宾 60fps。这些都是拟定验收目标，尚无本项目联机实测数据。

三人核心验证需要一个三人以上样本；现有《赤色要塞》可验证双人或观战媒体链路，但不能作为三人同时操作的验收样本。

## 9. 推荐实施范围与工作量

本次只细化方案。建议下一次开发确认范围为：**游戏多手柄验证＋iOS 双机到三机联机 POC**，默认三人同时操作为主目标，观战/轮换作为可选业务项。

| 工作包 | 粗估单人工作日 | 交付 |
| --- | --- | --- |
| B0 | 1–2 天，取决于样本与核心配置 | 三/四手柄能力记录、ROM 模式与端口映射 |
| B1+B2 | 3–5 天，真机反馈等待另计 | 固定版本三端验证入口、信令/TURN、连接和性能记录 |
| B3＋正式三人房间 | 4–6 天，前述通过后 | 固定席位、凭据、断线释放、三人房间 UI 与回归 |
